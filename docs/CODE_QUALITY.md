# Код сапасы — атаулар, құрылым, түсініктемелер

## Бастапқы тексеру

Тексерілген материал — жіберілген AirportJava.zip. GitHub-тағы кейінгі өзгерістер тексерілген жоқ.
Міндетті Java негіздері бастапқы кодта болды: 14 класс, FareCalculator интерфейсі, Ticket абстракт класы, мұрагерлік/полиморфизм, private өрістер, ArrayList/HashMap, BookingException, JSON сақтау.
Research/UML архивте жоқ, олардың кодпен сәйкестігі осы тексеруде расталмаған.
JUnit қосымша балл үшін енгізілді, міндетті талап ретінде көрсетілмейді.

## Не өзгерді және не үшін?

| Бұрын | Қазір | Себебі |
|---|---|---|
| Main ішінде мәзір, үлгі деректер, енгізу логикасы | Main + DemoData + ConsoleInput | Әр кластың міндеті анық |
| Main 299 жол | Main 224 жол | Үлгі деректер мен енгізу бөлек; жоба көлемі жалпы қысқарды деген сөз емес |
| service атауы | bookingService | Қай қызмет екенін нақты білдіреді |
| Күйлер бірнеше жерде мәтінмен жазылған | Booking.CREATED, CONFIRMED, CANCELLED, CHECKED_IN | Қате жазылу ықтималдығын азайту; JSON v1 және String getStatus сақталды |
| Билет түрін жасау екі жерде қайталанған | BookingService.createTicket | Ортақ ереже бір әдісте |
| Билетті броньмен іздеу Main және JsonStorage ішінде қайталанған | BookingService.findTicket | Іздеу бір жерде орындалады |
| Өткен рейс тек Main-де тексерілген | BookingService.createBooking ішінде | Басқа шақырушы да ережені айналып өте алмайды |
| Міндетті мәтін өрістері кейбір модельдерде тексерілмеген | Validation.requiredText | Бос ID/аты/тегі/кодты қабылдамайды, шеткі бос орындарды алып тастайды |
| Exception тек хабарлама сақтаған | cause конструкторы | Файл қатесінің бастапқы себебі жоғалмайды |
| Кейбір өзгермейтін сілтемелер қайта тағайындала алған | final өрістер | Объект құрылымын кездейсоқ ауыстырмау |
| Автоматты тесттер жоқ | 13 JUnit тесті | Ережелердің өзгерістен кейін сақталуын тексеру |

Мұндағы final коллекция элементтерін өзгертуге тыйым салмайды; сілтемені қайта тағайындауды шектейді.
Email үшін тек бос еместігі тексеріледі: форматты толық валидациялау енгізілген жоқ.
Flight.getAvailableSeats физикалық бос орындарды, BookingService.getRemainingCapacity броньға қолжетімді сыйымдылықты санайды. Мәзір екінші әдісті қолданады.

## Түсініктемелер

Барлық негізгі класқа қысқа JavaDoc қосылды. Маңызды себептер түсіндірілді:
- CHECKED_IN бронь орнын екі рет шегермеу;
- restoreBooking кезінде бұрынғы кодты, бағаны және билет уақытын сақтау;
- өткен рейске жаңа бронь жасамау, бірақ тарихи броньды оқуға рұқсат ету;
- JSON толық оқылғаннан кейін ғана қолданба тізімдерін ауыстыру;
- уақытша файлға жазу (электр өшкенде толық кепілдік дегенді білдірмейді).

## Қорғауда не ашып, не айту керек?

1. **Main.java:** «Бұл — кіру нүктесі мен мәзір. Үлгі деректерді және енгізу тексерулерін бөлек кластарға шығардым».
2. **DemoData.java және ConsoleInput.java:** «Бірі алғашқы деректерді жасайды, екіншісі дұрыс енгізуді сұрайды. Оларды Main шақырады».
3. **BookingService.java:** createBooking, createTicket, findTicket. «Бизнес ережесі қызметте тексеріледі; қайталанатын билет логикасын ортақ әдіске шығардым».
4. **Booking.java:** күй тұрақтылары және cancel. «Тек CREATED броньнан бас тартуға болады. Күй атаулары бір жерде берілген».
5. **Validation.java және Passenger.java:** «Бос міндетті өрісті объект құру кезінде тексереміз. Бірдей тексеру бірнеше класта қайталанбайды».
6. **JsonStorage.java:** loadState алдындағы түсініктеме және соңындағы тізім ауыстыру. «Қате JSON қолданба деректерін жартылай ауыстырмайды».
7. **AirportJavaTest.java:** тесттерді іске қос. «Тесттер броньдау ережелерін және JSON-нан қалпына келтіруді тексереді».

ЖИ көмегін жасырмай: «Кодты реттеуге ЖИ көмектесті. Мен кластардың міндеттерін түсіндіріп, бағдарламаны іске қосып көрсетемін» деп айтуға болады.

## Қосылмаған мүмкіндіктер

Код сапасы критерийі жаңа әкімші мәзірін немесе нақты банк төлемін талап етпейді. Қазіргі MVP сақталды. Research-та міндетті деп белгіленген әрекеттерді бөлек салыстыру қажет. Жаңа көмекші кластар мен findTicket әдісін Class UML-ға енгіз; ескі диаграмманы жойма.
